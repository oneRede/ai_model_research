# OlmoEarth 平台：行星级地理空间推理

[OlmoEarth 模型](https://allenai.org/blog/olmoearth-v1-1)是我们的地球观测基础模型（Earth observation foundation models）系列，在约 10 TB 的多模态卫星数据上进行预训练。政府机构、NGO 等使命驱动型组织正在用 OlmoEarth 进行森林砍伐监测、粮食安全和野火风险评估。

在 Ai2，我们知道如何训练和发布强大的开放模型。对于拥有强大工程团队的组织来说，一个开放模型就足够了。但环境领域的大多数组织恰恰最适合应用这些模型，却缺少相应的基础设施和工程团队来管理全流程：数据标注、模型微调、大规模推理。我们运营 [Skylight](https://allenai.org/skylight) 和 [EarthRanger](https://allenai.org/earthranger) 等平台已有十多年，全球用户每天依赖这些软件，因此它们必须每天正常工作。这段经历让我们明白，真正产生影响需要什么：在合适的时间和地点以经济高效的方式运行模型、监控性能、将原始输出转化为可操作的洞察，以及验证这些输出能够推动合作伙伴期望的结果。

这就是我们构建 [**OlmoEarth Platform**](https://allenai.org/olmoearth) 的原因：一个将地理空间模型从微调和评估带到大规模推理的基础设施。

这种规模的推理面临一系列独特挑战。需要从多个提供商那里查找和获取卫星影像，跨投影和分辨率进行对齐，并高效处理。然后，必须将结果拼接成地理一致的地图，同时基础设施还要从分布式计算的常规故障中恢复。

如今，该平台可在约一天内完成大陆级推理，处理数十 TB 的影像数据，成本仅为每平方公里几美分。开发这个平台意味着要面对一系列工程挑战，其他构建大规模地理空间系统的团队也会遇到这些挑战。本文将介绍这些挑战以及我们找到的解决方案。

### 为什么卫星推理具有挑战性

大多数 ML 模型接收几 MB 的数据，并在一秒内产生结果——比如 LLM 处理一段文本，或计算机视觉模型分析智能手机拍摄的照片。地球观测推理的规模完全不同——单个为基础模型微调以达到最佳性能的任务可能需要移动 TB 级数据并运行数小时。输入可能跨越大地理区域的多个光谱波段（spectral bands）、传感器类型和时间步长。它们可能来自多个提供商，每个提供商使用不同的投影和分辨率，并且可能包含缺失或被云层遮挡的观测数据。输出本身就是一张地图，因此每个预测都必须与周围区域保持相同投影和坐标网格的精确对齐。

即使是获取数据本身也可能是一个重大挑战。推理任务往往在数据下载和准备上耗时更多，而非模型运行本身，这使得高效的数据流水线至关重要。这些流水线必须处理大容量 I/O，同时提供重投影（reproject）和重采样（resample）影像所需的计算资源。

### 为任务选择合适的硬件

由于数据获取和准备通常主导推理任务的运行时间，将这些工作分配给 GPU，等于让最昂贵的硬件做 CPU 更擅长的事。因此，我们将每个任务分为三个阶段，每个阶段匹配不同的硬件配置：

- **数据获取和预处理（CPU，高 I/O）**：获取、重投影、对齐和归一化影像，然后以优化推理期间快速加载的格式写入。
- **推理（GPU）**：运行模型的前向传播（forward pass），并将最小处理的输出直接写入存储。
- **后处理（CPU）**：将每个窗口的输出拼接在一起，应用掩码或重新缩放，并以用户友好的格式（如 Zarr、GeoTIFF 或 GeoJSON）导出。

OlmoEarth Platform 将这些阶段分布在多台机器上，同时保持 GPU 的充分利用。多进程数据加载器持续为每个 GPU 提供数据，而完成的输出则直接流式传输到对象存储（blob storage）。

### 一个请求，数百个工作节点，数千个进程

**OlmoEarth Run** 是平台用于大规模推理任务的执行层，它将每个任务覆盖的地理区域划分为适合单个计算实例（工作节点）的分区（partitions），然后将这些分区细分为 OlmoEarth 模型处理的更小窗口（windows）。由于每个窗口可以在单独的前向传播中独立处理，因此地图一个部分的工作不需要等待另一个部分。

在实践中，一个州大小的区域可能会变成大约一百个分区，而大陆级运行可能会变成数千个分区。相邻分区略有重叠，我们在组装输出时协调这种重叠，以便最终栅格中不出现接缝。

由于分区是独立的，同一阶段可以同时在数千个计算实例上运行。我们最近用这种方法生成了北美全域的野火风险地图。在高峰期，该运行并行使用了约 19,600 个 CPU 和 994 个 GPU，网络吞吐量超过 168 GB/s。这种并行度将 4,737 小时的串行计算压缩到约 30.5 小时实际运行时间——155 倍的加速。

不过，扇出并不是无限的。更多的工作节点会触及云配额限制，因此并行度是每次运行的可调参数之一，我们可以根据单个任务进行调整。输出分辨率在数据量和计算与细节之间权衡；模型大小在 GPU 时间与准确性之间权衡；缓存原始影像在存储与同一区域重复运行的速度之间权衡。正确的设置取决于手头的任务——以及预算。

### 查找并获取正确的像素

给定一个地理区域和时间范围，平台首先必须确定哪些卫星场景应该输入模型。这意味着要在具有不同目录、格式和发布延迟的提供商之间识别捕获的内容、位置和时间。选择标准还取决于来源：对于 Sentinel-2 等光学影像，我们通常希望云量最少的场景，而对于合成孔径雷达（synthetic aperture radar），可用的极化通道可能更重要。

我们尽可能依赖公共 STAC 目录和开放标准。但大型推理任务可能会同时生成数千个元数据查询——远远超过 ESA 或 Microsoft Planetary Computer 的 STAC API 等外部服务设计处理的并发量。

为避免压垮这些服务，OlmoEarth Platform 维护自己的元数据索引，随着新影像的发布而更新。对于通过 AWS Open Data 托管的数据集，我们会收到每个新场景的 SNS 通知。当提供商不提供变更流（change stream）时，我们每隔几分钟轮询其上游索引。因此，我们对外部服务的请求遵循新发布的稳定节奏，而不是大型推理任务产生的突发请求。

每个索引条目存储场景元数据以及指向底层像素可用的每个位置的指针。在运行时，平台选择最佳来源，并对云优化格式（如 COG 或 Zarr）执行窗口化读取（windowed reads），仅检索给定分区所需的字节，而不是下载整个场景。

该索引还支持我们的标注工具。由于它维护指向云优化格式的 Sentinel-1、Sentinel-2、Landsat 和 NISAR 影像的指针，我们可以通过相同的窗口化读取系统从任何索引场景提供切片，而无需构建单独的数据摄取流水线。

使这一工作流程最简单的提供商具有三个特征，我们建议将其作为发布地球观测数据的最佳实践：新影像可用时基于队列的通知、在主要云平台上的存储而没有定制的速率限制或可用性瓶颈，以及支持范围读取的云优化格式。

### 大规模处理故障

OlmoEarth Platform 被设计为自动从故障中恢复。对于阶段和地理分区内的每个任务，它会动态配置一个运行我们的执行器 Docker 容器的虚拟机。`执行器`检索任务参数，执行工作，返回结果，然后关闭。由于每个任务都是可重入（reentrant）和幂等（idempotent）的，间歇性故障可以通过重新运行来安全处理。

在这种规模下，故障是预料之中的：提供商可能速度慢或暂时不可用；元数据可能表明影像存在，但所需的波段或窗口实际上缺失；云层覆盖可能导致可用观测太少；或者任务可能直接崩溃。平台通过任务跟踪、自动重试、在可用时回退到备用提供商，以及明确区分可重试错误和致命错误来响应。一个单独的监控进程检测已停滞或停止的执行器，并重新启动它们的任务。

### 未来发展方向

我们的路线图由合作伙伴发现的差距和他们最需要的能力所塑造。我们正在开展的工作领域包括：

- **自动化模型运行**：提前调度推理任务，或在影像索引注册感兴趣区域的新场景时触发它们。
- **变化检测和警报**：当用户监控的景观发生变化时通知他们，以便森林砍伐或洪水等事件以警报形式浮现，而不是需要手动查找和检查的栅格。
- **智能体工具和界面**：智能体（Agents）可以降低使用地理空间模型的门槛，从数据整理和特征工程到识别改进微调模型的方法。我们希望任何技术水平的用户都能完成以前需要经验丰富的 ML 研究人员才能完成的工作。
- **更快的模型**：与我们的研究团队合作开发更高效的架构，减少每个窗口的 GPU 时间。
- **更多模态**：将新的卫星传感器和数据源添加到 OlmoEarth 模型和支持它们的影像索引中。我们目前专注于整合气象数据（ERA-5）和提供更多环境因素细节的卫星。
- **嵌入模型**：开发专用的嵌入模型（embedding model），并在全球范围内预计算嵌入（embeddings）。对于许多任务，针对这些嵌入运行推理可以取代对原始影像的完整前向传播，使工作负载大大更快且更便宜。微调和直接推理对于在具有挑战性的任务上获得最大性能仍然很重要，但嵌入可以开启更广泛的高效应用。
- **随处运行**：OlmoEarth Run 只需要能够运行 Docker 镜像的虚拟机和对对象存储的访问。我们目前在 Google Cloud 上运行它，但该架构旨在支持多个云以及在合作伙伴自己的账户和计算环境中的部署。

这只是开始。地理空间基础模型，尤其是将它们投入运营，仍然是一项新兴技术，许多最适合使用它们的组织——那些从事保护、粮食安全、灾害响应和气候工作的组织——从未获得过这样的基础设施。这些团队需要了解地球的需求与他们的预算和技术资源允许他们做的事情之间的差距仍然很大。

我们正在构建 OlmoEarth 来帮助缩小这一差距。
