# OlmoEarth 平台：行星级地理空间推理

[OlmoEarth 模型](https://allenai.org/blog/olmoearth-v1-1)是我们的地球观测基础模型系列，在约 10 TB 的多模态卫星数据上进行预训练。这些模型已在多个实际项目中投入使用。政府机构、非政府组织等组织将它们应用于森林砍伐监测、灾害响应和粮食安全工作——通过 [Skylight](https://skylight.global/)（用于公海保护）、[EarthRanger](https://earthranger.com/)（用于野生动物保护）以及合作伙伴自己的系统。

但要让这些模型真正发挥作用，仅有模型权重还不够。还需要一个平台来微调模型以适应特定任务，在新数据上评估它们，并在洲际范围内高效运行推理——这些区域的卫星影像数据量达到数十 TB。OlmoEarth Platform 就是我们构建的这样一个系统。

本文介绍 **OlmoEarth Run**：这个平台的执行层，它接收用户查询（"在这个边界框内运行此模型"）并在地理空间数据处理、分布式计算和自动故障恢复的基础上实现它。OlmoEarth Run 使得在约一天内完成大陆级推理成为可能，每平方公里成本不到一美分——这使得全新类别的地理空间应用在技术上和经济上都变得可行。

## 为什么这很难

在行星级运行地理空间推理面临三个主要挑战：

**1. 数据量。** 即使是单个美国州的卫星影像也可能超过 1 TB。一个大陆级运行可能需要处理数十 TB 的输入数据。这些数据必须经过多个处理步骤：从多个提供商获取、对齐、重投影到统一坐标系统、重采样到目标分辨率。所有这些操作都是 I/O 和内存密集型的。

**2. 异构性。** 卫星影像来自不同的提供商、传感器和时间段。它们具有不同的投影、分辨率和光谱波段。模型期望的输入格式通常与任何单个来源不同，因此流水线必须动态对齐和转换数据。

**3. 容错性。** 在数千个工作节点上运行数百或数千小时的计算时，故障不可避免。网络超时、实例抢占和瞬态存储错误都会发生。如果没有强大的检查点和恢复机制，单个故障就可能导致整个任务失败。

OlmoEarth Run 的设计直接解决这些挑战。

## 三阶段流水线

OlmoEarth Run 将推理工作负载分为三个连续阶段，每个阶段都针对其特定操作进行优化：

**阶段 1：预处理（CPU）。** 这个阶段从 Blob 存储（对象存储）获取原始卫星影像，然后执行一系列转换：重投影到统一的坐标参考系统（例如 Web Mercator）、重采样到目标分辨率，最后将对齐的数据写入 Zarr（一种云原生数组格式）。预处理在 CPU 实例上运行，这些实例针对大型数据集的并行 I/O 进行了优化。

**阶段 2：推理（GPU）。** 对齐的数据从 Zarr 读取，分批传递给 OlmoEarth 模型，模型的输出作为另一个 Zarr 数组写回。这个阶段在 GPU 实例上运行，最大化推理吞吐量。

**阶段 3：后处理（CPU）。** 最终阶段将模型输出（通常是栅格预测）转换为最终格式，例如 GeoTIFF 或 GeoJSON。它可能还包括后处理步骤，如阈值化、矢量化或与其他地理空间图层的合并。后处理再次在 CPU 上运行，确保最终工件易于集成到下游工作流中。

将流水线分为 CPU 和 GPU 阶段带来两个关键优势：可以独立扩展每个部分，并为每个工作负载选择最佳实例类型。这种设计降低了成本并提高了资源利用率。

## 分区并行

要在洲际范围内运行推理，OlmoEarth Run 将作业分解为独立的**分区**。每个分区对应地图的一个空间区域。系统将作业分割成适合单个计算实例（工作节点）大小的分区，然后将这些分区再细分为更小的**窗口**，供 OlmoEarth 模型处理。由于每个窗口可以在单独的前向传递中独立处理，地图一部分的工作无需等待另一部分。

在实践中，一个州大小的区域可能变成一百个左右的分区，而大陆级运行可能变成数千个分区。相邻分区略有重叠，我们在组装输出时协调这种重叠，使最终栅格中不会出现接缝。

由于分区是独立的，同一阶段可以同时在数千个计算实例上运行。我们最近使用这种方法生成了覆盖整个北美的野火风险地图。在高峰期，运行使用了约 19,600 个 CPU 和 994 个 GPU 并行工作，网络吞吐量超过 168 GB/s。这种并行度将估计 4,737 小时的串行计算减少到约 30.5 小时的实际时间——**155 倍加速**。

## 自动故障恢复

在如此规模的分布式系统中，故障是常态而非例外。实例可能被抢占，网络请求可能超时，临时存储错误可能使读取失败。OlmoEarth Run 通过以下机制容错：

**1. 检查点。** 每个分区的进度在 Blob 存储中持续跟踪。如果工作节点失败，系统会检测到这一点，并将分区重新分配给另一个工作节点，该工作节点从检查点恢复。

**2. 重试逻辑。** 瞬态错误（如网络超时或临时的 Blob 存储不可用）会自动重试，采用指数退避策略。

**3. 幂等性。** 所有阶段都被设计为幂等的（多次执行产生相同结果）：重新运行分区会产生与第一次相同的结果。这确保了重试不会破坏部分完成的工作。

这些机制的组合使得 OlmoEarth Run 能够在大规模任务中保持稳定运行，即使个别组件失败也不受影响。在实践中，我们观察到大规模作业的完成率超过 99%，无需人工干预即可从瞬态故障中恢复。

## 性能与成本

OlmoEarth Run 针对性能和成本进行了优化。通过选择每个阶段的正确实例类型——预处理和后处理使用 CPU 密集型实例，推理使用 GPU 加速实例——我们最大化了利用率并最小化了空闲时间。

分区并行意味着工作在尽可能多的实例之间分配，将实际时间降至最低。对于典型的大陆级运行，端到端延迟约为 24 小时，每平方公里成本不到一美分。这使得以前在技术上或经济上不可行的应用——如月度森林砍伐监测或近实时野火风险评估——变得切实可行。

## 可扩展性与可移植性

OlmoEarth Run 的架构从一开始就考虑了可扩展性和可移植性：

- **可组合的模块。** 流水线的每个阶段都是一个独立的模块，具有明确定义的输入和输出。这使得添加新的预处理步骤、交换不同的模型或插入自定义后处理逻辑变得简单。
- **与模型无关。** 虽然 OlmoEarth Run 是为 OlmoEarth 模型构建的，但它可以运行任何接受地理空间栅格作为输入并产生栅格或矢量输出的模型。用户可以带来自己微调的模型或嵌入，新的应用可能会打开更广泛的高效应用范围。
- **随处运行。** OlmoEarth Run 只需要能够运行 Docker 镜像的虚拟机和对 Blob 存储的访问。我们目前在 Google Cloud 上运行它，但架构设计支持多云部署以及在合作伙伴自己的账户和计算环境中部署。

这只是开始。地理空间基础模型，尤其是将它们投入运营，仍然是一项新兴技术，而许多最适合使用它们的组织——那些从事保护、粮食安全、灾害响应和气候工作的组织——从未获得过这样的基础设施。这些团队需要了解地球的信息与他们的预算和技术资源所允许的之间的差距仍然很大。

我们正在构建 OlmoEarth 来帮助缩小这一差距。
